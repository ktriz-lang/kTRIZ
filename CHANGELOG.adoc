= Changelog

All notable changes to kTRIZ are documented here. The project is pre-1.0
and the API is unstable -- breaking changes may happen in any release
without a deprecation period.

== Unreleased

=== Benchmark calibration set

* New `benchmark/calibration-set.csv`: six sourced contradiction cases (three WIPO
  Tool 13, two Stevko et al. 2023, one MATRIZ Wiki) with improving and worsening
  parameter, sources, licence and a confidence level (three `high`, three `low`).
* Documentation `docs/calibration-set.adoc` (column format, confidence levels,
  attribution, gap to a real gold set) and a `NOTICE` entry for the CC BY 4.0 sources.
* New `CalibrationSetTest` validates the file (header, field counts, ids, parameter
  ranges, matrix cells, principle lists, https sources, confidence vocabulary). Gradle
  hands the CSV path to the test as the system property `ktriz.calibration.csv`.
* Explicitly not a gold set: six cases, no independent second annotator, and no
  model results. No scorer or harness is included.
* Tests: 468 (was 453).

=== Evolution laws

* New `EvolutionLaw` enum (eight classical laws of technical systems evolution,
  ids 1..8, English label, own short description) and `EvolutionLawGroup`
  (statics, kinematics, dynamics; grouped 3 + 3 + 2) in `ktriz-core`.
* New MCP tool `list_evolution_laws` (the thirteenth tool); `dev.ktriz.evolution.*`
  is a default script import.
* Provenance record `docs/evolution-laws-provenance.adoc` and a `NOTICE` entry.
* Deliberately no `labelDe`, no ninth law (single source), no evolution lines,
  patterns or TESE trends, and no application DSL.
* Tests: 453 (was 445).

=== Rendering

* `FunctionModel.renderSvg()` routes dense edge bundles (two or more edges
  between the same component pair) onto distinct anchor points along the node
  box side instead of letting every line converge on the same spot: anchors
  are spread evenly (12 px corner inset, about 14 px apart where the box
  allows), edges running in the same direction sit together, and the bowed
  lines no longer cross at their ends. The self-loop band on the right side
  stays free of anchors.
* A component carrying a bundle is widened to fit its anchors (capped at
  320 px); other components and models without a bundle render byte-identically
  to before (guarded by reference-SVG tests, also for Su-Field output).
* Wavy (`HARMFUL`) strokes inside a bundle use an amplitude of at most 40% of
  the gap to the neighbouring anchor.
* Known limit: with more than about 37 edges between one pair the anchors are
  closer than an arrowhead is wide (8 px) and neighbouring arrowheads touch;
  verb labels of dense bundles can still cross neighbouring lines.
* Tests: 445 (was 423) -- 15 unit tests for anchor distribution and node sizing
  now live in `ktriz-render-kuml` (internal functions are not visible from
  `ktriz-tests`), 7 new render tests in `ktriz-tests`; one existing test now
  measures the bow offset signed instead of absolute, because mirrored edges
  of a bundle no longer land on identical distances from the node axis.

=== Documentation

* Guide titles under `docs/` now read `kTRIZ guide: ...` (no more duplicated
  title and first heading); the MCP guide points to the build step instead of
  an install step that did not exist.

== v0.3.0 -- 2026-10-23

=== Physical contradictions

* ARIZ is deliberately not modelled: sources disagree on the step level and
  the licence is unclear; see `docs/ariz-provenance.adoc`.

* New package `dev.ktriz.physical`: `PhysicalContradiction` +
  `physicalContradiction { }` DSL (element, property, two states with optional
  reasons, optional declared separation) and the `SeparationPrinciple` enum
  (the four classical principles; not the Mann/CREAX set).
* No mapping from separation principles to inventive principles is bundled:
  only one freely available source was found, below the two-source rule; see
  `docs/physical-contradictions-provenance.adoc`.
* `dev.ktriz.physical.*` is now a default import in `.ktriz.kts` scripts.
* KDoc fix in `Contradiction`: it no longer claims ADR-0001 defers physical
  contradictions.

=== MCP server (physical contradictions)

* New tool `build_physical_contradiction` (validation plus Kotlin snippet).
* New tool `list_separation_principles`.

=== MCP server

* New tool `render_su_field_svg`: renders a validated Su-Field triangle as
  SVG (same arguments as `build_su_field`).
* New tool `render_function_model_svg`: renders a function model as SVG
  (same arguments as `build_function_model`) with tighter limits -- 60
  components (auto-declared edge endpoints included), 150 edges, 20,000
  characters of names and verbs in total.
* New tool `lookup_standard_solution`: the 76 standard solutions by `code`,
  by `standardClass`, or all at once. The texts are the ones already
  shipped in `StandardSolution`; no new text, and still no bridge from
  `SuField` to a solution.
* Render calls run on daemon worker threads under a 10 s deadline with at
  most 2 concurrent renders and a 2,000,000-character output cap; new
  structured errors `render_timeout`, `render_busy`,
  `render_output_too_large` and `unknown_standard_solution`.
* `ktriz-mcp` now depends on `ktriz-render-kuml` (ELK, EMF and Guava come in
  transitively, the distribution grows). The `ktriz-mcp` and `ktriz` start
  scripts pass `-Djava.awt.headless=true`, and both `main` functions set it
  first thing.
* Corrected tool descriptions: `list_standard_solution_classes` no longer
  claims that the 76 solution texts are not bundled, and `build_su_field`
  now points to `render_su_field_svg`.

=== Renderer fixes

* `FunctionModel.renderSvg()`: edge-verb labels are now placed by a greedy
  2D collision-avoidance search instead of a fixed vertical stagger --
  each label tries a bounded set of candidate positions (alternating
  above/below the route's midpoint, stepping out by the label's own
  measured height) and keeps whichever has the least overlap area against
  every label and node box already placed; a verb that still cannot avoid
  overlap is truncated with an ellipsis (full text kept in a `<title>`
  tooltip) and re-searched. Fixes label/label and label/node overlap for
  dense edge bundles and long verbs that the old fixed-step stagger could
  not avoid.
* `bowOffsetFor`/`selfLoopRadiusPx`: the previous hard clamps
  (`BOW_MAX_OFFSET_PX = 27`, `SELF_LOOP_STACK_MAX_PX = 44`) have been
  removed. Both now use an adaptive envelope that narrows the per-edge
  spacing as the group grows (`BOW_ENVELOPE_PX = 90` / `BOW_MIN_SPACING_PX
  = 3` for bowed edges, `SELF_LOOP_ENVELOPE_PX = 120` /
  `SELF_LOOP_MIN_STACK_STEP_PX = 3` for self-loops) instead of collapsing
  every edge past a fixed group size onto the same outermost offset or
  radius.

== v0.2.0 -- 2026-09-06

=== Substance-field models

* `StandardSolutionClass` (module `ktriz-core`) enumerates the 5 classical
  groups the 76 standard inventive solutions fall into (13/23/6/17/17), each
  with an English/German label, description and `solutionCount`. Sourced
  from the MATRIZ wiki's CC-licensed classification -- a stable, low-detail
  primary source found after two weaker full-76-text candidates were
  researched and rejected (see `docs/standard-solutions-provenance.adoc`).
* `StandardSolution` (module `ktriz-core`) enumerates the 76 individual
  classical TRIZ standard solutions -- classical dot-numbered code (e.g.
  `"1.1.1"`), owning `StandardSolutionClass`, and a short English "what to
  do" statement per solution -- with an `ofCode(code)` lookup. Transcribed
  from a single 5-part TRIZ Journal article series (Terninko, Domb & Miller,
  2000), not a majority-reconciled compilation like the contradiction
  matrix; see `docs/standard-solutions-provenance.adoc` for the full
  sourcing record and caveats (including the `5.1.1` numbering anomaly).
  As with `StandardSolutionClass`, there is deliberately no bridge function
  from a `SuField`/`SuFieldQuality` to a specific `StandardSolution`, and
  `StandardSolution.ofCode(...)` is not yet exposed as its own MCP tool.
* `SuField.renderSvg()` (module `ktriz-render-kuml`) renders a `suField { }`
  model to a standalone SVG document: the classical S1-S2-Field triangle,
  F at the apex, S1 bottom-left, S2 bottom-right, action reading
  right-to-left from S2 into S1. Unlike `FunctionModel.renderSvg()`, this
  path never invokes kUML's ELK layout engine -- the triangle's geometry is
  fixed and deterministic, confirmed against two independent primary
  sources on classical Su-Field notation. `SuFieldQuality` reuses
  `FunctionQuality`'s existing stroke vocabulary (solid/dashed/doubled/wavy)
  rather than inventing a second one, per MATRIZ's own statement that
  Su-Field interaction symbols mirror function-modeling symbols; an
  `INCOMPLETE` triangle draws no base line at all. `FieldType` gained a
  fourth field, `abbreviation`, carrying the classical subscript (`Mec`,
  `Th`, `Ch`, `El`, `M`, `Gr`) used in the printed `F`-symbol notation.
* `ktriz-script`'s default imports now also include `dev.ktriz.sufield.*`,
  so `suField { }` (and `SuField.renderSvg()`, via the existing
  `dev.ktriz.render.kuml.*` default import) are callable from a
  `.ktriz.kts` script with no explicit import, matching `functionModel { }`.
* Hardened `xmlEscapeText` (module `ktriz-render-kuml`) to strip characters
  XML 1.0 forbids outright (control characters, unpaired surrogates) before
  escaping -- closes a latent defect shared by both SVG renderers where a
  component/substance name containing such a character produced an
  unparseable document.

=== AI tooling

* Three new MCP tools in `ktriz-mcp`, mirroring the existing
  `build_function_model` pattern: `build_su_field` (validates through the
  same `SuField` construction logic as the DSL, and returns a ready-to-use
  `suField { }` Kotlin snippet in `structuredContent` on success),
  `list_field_types` and `list_standard_solution_classes` (few-shot
  catalogue tools). No `render_su_field_svg` MCP tool, for consistency with
  `build_function_model` -- rendering stays CLI-/script-only.

=== Project infrastructure

* A GitHub Actions CI workflow (`.github/workflows/ci.yml`) runs
  `./gradlew clean check` on every push/PR to `master` -- kTRIZ's first CI
  pipeline.

== v0.1.0 -- 2026-09-02

First tagged snapshot. Everything below already exists on `master` before
this tag; the tag exists to give the current state of the project a stable,
citable reference point, not to mark a sudden jump in functionality.

=== Contradiction spine

* All 39 classical Altshuller engineering parameters and all 40 classical
  inventive principles, as Kotlin `enum class`es with English and German
  labels -- existence is a compiler-enforced guarantee, not a runtime check.
* `Contradiction` + the `contradiction { }` factory, with a compile-time
  existence check and a runtime well-formedness check (a parameter cannot
  contradict itself).
* The full classical 39x39 contradiction matrix (1248 populated cells),
  reconciled from four independent, freely available transcriptions under a
  documented majority-rule process -- see `docs/matrix-provenance.adoc` and
  kTRIZ-ADR-0003. Matrix 2003/2010/2022 (Darrell Mann/CREAX, proprietary,
  48 parameters) was never consulted and is structurally rejected by the
  parser.
* A pluggable matrix-source seam: `ContradictionMatrixSource.fromFile(path)`
  loads an operator-supplied matrix file through the same hardened,
  size-capped, URI-scheme-restricted gate and parser as the bundled data;
  the system property `ktriz.matrix.file` swaps `ContradictionMatrix`'s own
  process-wide default with no code change.

=== Function models

* `functionModel { }` -- a small DSL for TRIZ function analysis: `Component`
  nodes and `FunctionEdge`s judged `USEFUL`/`HARMFUL`/`INSUFFICIENT`/
  `EXCESSIVE`, with automatic component dedup by name and accepted
  self-loops.
* `FunctionModel.renderSvg()` (module `ktriz-render-kuml`) renders a
  function model to a standalone SVG document, using kUML's
  `kuml-layout-api`/`kuml-layout-elk` purely as a graph-layout engine (no
  kUML metamodel, no kUML SVG renderer). Node boxes size from real
  font-metrics measurement, every edge gets an arrowhead oriented from its
  own route geometry, multiple edges between the same component pair bow
  apart and their labels stagger to stay readable, and self-loops draw a
  dedicated fixed-radius arc.

=== Substance-field models

* `suField { }` -- a small DSL for TRIZ substance-field (Su-Field) analysis:
  an object substance S1, an optional second substance S2 acted on through
  an optional `FieldType` (the six classical Altshuller field types --
  mechanical, thermal, chemical, electric, magnetic, gravitational), judged
  overall by a `SuFieldQuality` (`COMPLETE`/`INCOMPLETE`/`INSUFFICIENT`/
  `EXCESSIVE`/`HARMFUL`). An MCP tool, `build_su_field`, plus
  `list_field_types`/`list_standard_solution_classes` catalogue tools, are
  *done* -- see the "AI tooling" entry below. Deliberately still out of
  scope: a lookup engine over the 76 standard inventive solutions.

=== AI tooling

* An MCP server (module `ktriz-mcp`) exposing the 39 parameters, the 40
  principles, the deterministic contradiction-matrix lookup,
  function-model construction, and Su-Field model construction
  (`build_su_field`) plus Su-Field/standard-solution-class catalogues
  (`list_field_types`, `list_standard_solution_classes`) as tools over
  stdio, for LLM agents. Wired into the CLI as `ktriz mcp`.
* A `*.ktriz.kts` Kotlin scripting host (module `ktriz-script`) that
  compiles and runs a script with `dev.ktriz.core.*`/`dev.ktriz.function.*`/
  `dev.ktriz.render.kuml.*` in scope by default -- no imports needed, and
  `FunctionModel.renderSvg()` is directly callable from a script. Every
  outcome (success, compile error, runtime error) maps to a structured
  `KtrizScriptOutcome` with a stable `KTRIZ-S-xxx` code, never a raw
  exception or stack trace -- the generate-compile-repair signal the whole
  project is built around. Exposed on the command line as `ktriz run`, with
  a `--output json` mode for machine consumers.

=== Not yet included

* The 76 standard inventive solutions (Su-Field lookup/repair engine).
* SVG rendering of Su-Field triangles.
* Physical contradictions, ARIZ as a guided workflow, evolution trends --
  explicitly deferred past V1, see kTRIZ-ADR-0001.
* Any published artifact (Maven Central, Homebrew, SDKMAN!) -- this tag is
  source-only.
