= kTRIZ

image::docs/images/ktriz-banner.png[kTRIZ — Kotlin TRIZ DSL,link=https://github.com/ktriz-lang/kTRIZ]

Type-safe Kotlin DSL for TRIZ (Theory of Inventive Problem Solving).

WARNING: kTRIZ is pre-release software. The current tag is `v0.3.1` (source
only: there is no published artifact on Maven Central or Homebrew), the API
is unstable, and breaking changes may happen in any release. What exists: the
contradiction spine with the full classical 39x39 matrix, function models and
substance-field (Su-Field) models with SVG rendering, the 76 standard
solutions, physical contradictions with the four classical separation
principles, the `*.ktriz.kts` scripting host (`ktriz run`), and an MCP server
with twelve tools (`ktriz mcp`). Scripts run without a sandbox -- do not run
untrusted code. Whether EU database rights attach to the bundled matrix
compilation is not conclusively settled (see link:docs/contradiction-matrix.adoc#matrix[Contradiction matrix data]). Deliberately not
built: ARIZ (see link:docs/ariz-provenance.adoc[docs/ariz-provenance.adoc]) and
a mapping from separation principles to the 40 inventive principles (see
link:docs/physical-contradictions.adoc#physical-contradiction[Physical contradictions]).

== Why kTRIZ

Large language models are strong in mainstream, high-resource languages like
Kotlin and weak in obscure, low-resource domain-specific notations. TRIZ today
mostly lives in flipcharts, spreadsheet transcriptions of the classical
contradiction matrix, and scanned PDF tables -- none of it compiler-checkable,
all of it easy for an LLM to hallucinate against (an invented parameter name,
a swapped improving/worsening direction, a matrix cell that does not exist).

kTRIZ turns TRIZ's core vocabulary -- engineering parameters, inventive
principles, contradictions and the contradiction matrix -- into ordinary
Kotlin types. An LLM that names a nonexistent parameter simply fails to
compile; the compiler becomes the oracle that catches the mistake before a
human ever sees it. This is the same Typed Domain Grounding idea behind the
sibling projects kUML (models for the IT domain) and kSTEP (STEP/EXPRESS for
mechanical engineering) -- kTRIZ applies it to inventive problem solving.

== Status

What works today (v0.3.1, pre-release, source only; 445 Kotest test cases):

* The contradiction spine: all 39 engineering parameters and 40 inventive
  principles as Kotlin enums with English and German labels, `Contradiction`
  with a compiler-enforced existence check, and a deterministic lookup over the
  full classical 39x39 matrix (1248 populated cells).
* Function models (`functionModel { }`) and substance-field models
  (`suField { }`), both with SVG rendering, plus the 76 classical standard
  solutions.
* Physical contradictions (`physicalContradiction { }`) with the four
  classical separation principles.
* A `*.ktriz.kts` scripting host (`ktriz run`) and an MCP server with twelve
  tools (`ktriz mcp`) for LLM agents.

[#hello-world]
== Hello World

This first example is plain Kotlin; the equivalent as a `.ktriz.kts` script
is shown in link:docs/scripting.adoc#scripting[Running a script].

[source,kotlin]
----
import dev.ktriz.core.EngineeringParameter
import dev.ktriz.core.contradiction
import dev.ktriz.core.resolve

fun main() {
    // "I want to make the chassis lighter, but as soon as I remove material
    //  it becomes too weak and breaks."
    val problem =
        contradiction(
            improving = EngineeringParameter.WEIGHT_OF_MOVING_OBJECT,
            worsening = EngineeringParameter.STRENGTH,
        )

    println("Contradiction: ${problem.improving.labelEn} up vs. ${problem.worsening.labelEn} down")
    problem.resolve().forEach { p -> println("  #${p.id}  ${p.labelEn}") }
}
----

Expected output:

----
Contradiction: Weight of moving object up vs. Strength down
  #28  Mechanics substitution
  #27  Cheap short-living objects
  #18  Mechanical vibration
  #40  Composite materials
----

[#the-compiler-as-oracle]
== The compiler as oracle

Ask an LLM to improve "chassis weight" against a made-up parameter, and the
mistake shows up as an ordinary Kotlin compiler error rather than as a subtly
wrong recommendation:

----
Unresolved reference 'STRUCTURAL_INTEGRITY'.
----

That error message is itself a repair signal a generate-compile-repair loop
can act on -- there is no such thing as a plausible-looking but wrong
parameter name in kTRIZ, because parameters that do not exist do not compile.
link:docs/scripting.adoc#scripting[In the scripting guide], the same error appears in its fully structured form, as
`ktriz run` reports it via a `KtrizScriptOutcome.CompilationError` with the
line/column the diagnostic points at -- the shape a generate-compile-repair
loop actually consumes, not just the raw compiler text.

== Modules

[cols="1,3"]
|===
| Module | Purpose

| `ktriz-core`
| The DSL itself: `EngineeringParameter`, `InventivePrinciple`, `Contradiction`, `ContradictionMatrix`, `ContradictionMatrixSource`, `functionModel`, `suField`, `physicalContradiction`, `SeparationPrinciple`. Bundles the classical 39x39 contradiction matrix as a classpath resource (`contradiction-matrix-1971.csv`). No dependencies beyond the Kotlin standard library and the `kotlin-logging` facade (no logging backend -- the runnable modules bring their own).

| `ktriz-script`
| The `*.ktriz.kts` scripting host: `KtrizScript`/`KtrizScriptCompilationConfiguration`, `KtrizScriptHost.eval`/`evalSource`, `KtrizScriptOutcome`. `api ktriz-core` (not `implementation`) so `ktriz-core` types resolve inside a script's `wholeClasspath = true` compilation. Deliberately unsandboxed -- see link:docs/scripting.adoc#scripting[Running a script].

| `ktriz-cli`
| Command-line entry point. `ktriz mcp` (see link:docs/mcp-server.adoc#mcp[MCP server]); `ktriz run <script.ktriz.kts> [--output json]` (see link:docs/scripting.adoc#scripting[Running a script]); `ktriz help`.

| `ktriz-render-kuml`
| Renders `functionModel { }` and `suField { }` to SVG. Depends on `ktriz-core` and kUML's `kuml-layout-api`/`kuml-layout-elk` for the function-model path (layout only, no kUML metamodel/rendering dependency); the Su-Field path uses only kUML's plain geometry types (`Point`/`Rect`/`Size`), never the layout engine itself -- see link:docs/substance-field-models.adoc#su-field-svg[Rendering a substance-field model].

| `ktriz-mcp`
| MCP server exposing the DSL to LLM agents as tools over stdio. Depends on `ktriz-core` and `ktriz-render-kuml` (pulls ELK/EMF/Guava transitively; runs headless); also reachable via `ktriz mcp` in `ktriz-cli` (see link:docs/mcp-server.adoc#mcp[MCP server]).

| `ktriz-tests`
| Kotest test suite for `ktriz-core`, `ktriz-script`, `ktriz-render-kuml`, `ktriz-mcp`, and `ktriz-cli`.
|===
