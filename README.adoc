= kTRIZ

image::docs/images/ktriz-banner.png[kTRIZ — Kotlin TRIZ DSL,link=https://github.com/ktriz-lang/kTRIZ]

Type-safe Kotlin DSL for TRIZ (Theory of Inventive Problem Solving).

WARNING: kTRIZ is in very early, pre-release development (M1, wave 6). The
core contradiction spine, the function model and SVG rendering for the
function model exist, the contradiction matrix is fully populated with the
classical 39x39 table (1248 cells, see <<matrix>>), an MCP server exposes
it all to LLM agents (see <<mcp>>), and a `*.ktriz.kts` scripting host is
usable via `ktriz run` (see <<scripting>>). `ktriz run` and `ktriz mcp` both
exist; no published artifact. The API is unstable.

Licensed under the Apache License, Version 2.0. See link:LICENSE[LICENSE].

== Why kTRIZ

Large language models are strong in mainstream, high-resource languages like
Kotlin and weak in obscure, low-resource domain-specific notations. TRIZ today
mostly lives in flipcharts, spreadsheet transcriptions of the classical
contradiction matrix, and scanned PDF tables -- none of it compiler-checkable,
all of it easy for an LLM to hallucinate against (an invented parameter name,
a swapped improving/worsening direction, a matrix cell that does not exist).

kTRIZ turns TRIZ's core vocabulary -- engineering parameters, inventive
principles, contradictions and the contradiction matrix -- into ordinary
Kotlin types. An LLM that names a nonexistent parameter simply fails to
compile; the compiler becomes the oracle that catches the mistake before a
human ever sees it. This is the same Typed Domain Grounding idea behind the
sibling projects kUML (models for the IT domain) and kSTEP (STEP/EXPRESS for
mechanical engineering) -- kTRIZ applies it to inventive problem solving.

== Status

What works today:

* All 39 classical Altshuller engineering parameters, as a Kotlin `enum` with
  English and German labels.
* All 40 classical inventive principles, same shape.
* `Contradiction` + the `contradiction { }` factory, with a compiler-enforced
  existence check (an invented parameter does not compile) and a runtime
  well-formedness check (a parameter cannot contradict itself).
* `ContradictionMatrix.lookup(...)` / `Contradiction.resolve()` -- a pure,
  deterministic matrix lookup over the full classical 39x39 matrix, 1248
  populated cells, loaded from a bundled classpath resource (see <<matrix>>).
* A pluggable matrix-source seam: `ContradictionMatrixSource.fromFile(path)`
  loads an operator-supplied matrix file through the same hardened gate and
  parser as the bundled data, and the system property `ktriz.matrix.file`
  swaps `ContradictionMatrix`'s own process-wide default with zero code
  changes (see <<matrix>>).
* `functionModel { }` -- a small DSL for TRIZ function analysis: `Component`
  nodes and `FunctionEdge`s judged `USEFUL`/`HARMFUL`/`INSUFFICIENT`/
  `EXCESSIVE`, with automatic component dedup by name (see <<function-model>>).
* `FunctionModel.renderSvg()` (module `ktriz-render-kuml`) -- renders a
  `functionModel { }` to a standalone SVG document, using kUML's
  `kuml-layout-api`/`kuml-layout-elk` purely as a graph-layout engine (no
  kUML metamodel, no kUML SVG renderer). `FunctionQuality` maps to a stroke
  treatment: `USEFUL` solid, `INSUFFICIENT` dashed, `EXCESSIVE` a doubled
  line, `HARMFUL` a wavy path (see <<function-model-svg>>).
* An MCP server (module `ktriz-mcp`) exposing the 39 parameters, the 40
  principles, the deterministic matrix lookup, and TRIZ function-model
  validation as tools over stdio, for LLM agents (see <<mcp>>).
* A `*.ktriz.kts` Kotlin scripting host (module `ktriz-script`,
  `KtrizScriptHost.eval`/`evalSource`) that compiles and runs a script with
  `dev.ktriz.core.*`/`dev.ktriz.function.*` in scope by default, mapping every
  outcome -- success, compile error, runtime error -- into a structured
  `KtrizScriptOutcome` with a stable `KTRIZ-S-xxx` code, never a raw exception
  or stack trace. Exposed on the command line as `ktriz run` (see <<scripting>>).
* 216 Kotest test cases covering the above.

What does not exist yet: a way to call `FunctionModel.renderSvg()` from
inside a script. See <<roadmap>>.

[#hello-world]
== Hello World

This first example is plain Kotlin; the equivalent as a `.ktriz.kts` script
is shown in <<scripting>>.

[source,kotlin]
----
import dev.ktriz.core.EngineeringParameter
import dev.ktriz.core.contradiction
import dev.ktriz.core.resolve

fun main() {
    // "I want to make the chassis lighter, but as soon as I remove material
    //  it becomes too weak and breaks."
    val problem =
        contradiction(
            improving = EngineeringParameter.WEIGHT_OF_MOVING_OBJECT,
            worsening = EngineeringParameter.STRENGTH,
        )

    println("Contradiction: ${problem.improving.labelEn} up vs. ${problem.worsening.labelEn} down")
    problem.resolve().forEach { p -> println("  #${p.id}  ${p.labelEn}") }
}
----

Expected output:

----
Contradiction: Weight of moving object up vs. Strength down
  #28  Mechanics substitution
  #27  Cheap short-living objects
  #18  Mechanical vibration
  #40  Composite materials
----

[#function-model]
== Function model

A second small DSL, `functionModel { }`, models TRIZ function analysis: which
components exist, and which functions connect them, judged useful, harmful,
insufficient, or excessive.

[source,kotlin]
----
import dev.ktriz.function.functionModel

val fm = functionModel {
    val engine = component("Engine")
    val coolant = component("Coolant")
    val block = component("Cylinder block")
    useful(from = coolant, to = engine, verb = "cools")
    harmful(from = engine, to = block, verb = "overheats")
    insufficient(from = coolant, to = engine, verb = "circulates")
}

println("${fm.components.size} components, ${fm.edges.size} functions")
fm.edges.forEach { e -> println("  ${e.from.name} --[${e.quality}]--> ${e.to.name} (${e.verb})") }
----

Expected output:

----
3 components, 3 functions
  Coolant --[USEFUL]--> Engine (cools)
  Engine --[HARMFUL]--> Cylinder block (overheats)
  Coolant --[INSUFFICIENT]--> Engine (circulates)
----

Components declared by name are deduped automatically -- `component("Engine")`
can be called again at any later edge site and always returns the same node,
so callers do not need to pre-declare every component before using it.
Self-loops (a component acting on itself, e.g. a part wearing itself out) are
accepted on purpose -- see the KDoc on `FunctionModelBuilder` for the
reasoning.

[#function-model-svg]
== Rendering a function model

The `ktriz-render-kuml` module renders any `functionModel { }` to a
standalone SVG document:

[source,kotlin]
----
import dev.ktriz.function.functionModel
import dev.ktriz.render.kuml.renderSvg

val fm = functionModel {
    val engine = component("Engine")
    val coolant = component("Coolant")
    val block = component("Cylinder block")
    useful(from = coolant, to = engine, verb = "cools")
    harmful(from = engine, to = block, verb = "overheats")
    insufficient(from = coolant, to = engine, verb = "circulates")
}

File("function-model.svg").writeText(fm.renderSvg())
----

kUML is used here strictly as a *layout* library, not as a diagram renderer:
`ElkLayoutEngine` (from `kuml-layout-elk`) computes node positions and edge
routes for the component graph, and kTRIZ owns the actual SVG markup and the
mapping from `FunctionQuality` to stroke style. This split exists because
kUML's own SVG renderer (`kuml-io-svg`) is built around specific metamodel
packages (UML, C4, SysML2, BPMN, Blueprint, ERM) with per-relationship-subtype
hardcoded line styles and no generic node/edge diagram entry point a
`FunctionModel` could plug into -- and no wavy/doubled-line concept a
`FunctionQuality` could map onto. `USEFUL` renders as a plain solid stroke,
`INSUFFICIENT` as a dashed stroke, `EXCESSIVE` as two parallel lines (the
engineering-drawing convention for an over-strong connection), and `HARMFUL`
as a sine-perturbed wavy path.

[#the-compiler-as-oracle]
== The compiler as oracle

Ask an LLM to improve "chassis weight" against a made-up parameter, and the
mistake shows up as an ordinary Kotlin compiler error rather than as a subtly
wrong recommendation:

----
Unresolved reference 'STRUCTURAL_INTEGRITY'.
----

That error message is itself a repair signal a generate-compile-repair loop
can act on -- there is no such thing as a plausible-looking but wrong
parameter name in kTRIZ, because parameters that do not exist do not compile.
<<scripting,Below>>, the same error appears in its fully structured form, as
`ktriz run` reports it via a `KtrizScriptOutcome.CompilationError` with the
line/column the diagnostic points at -- the shape a generate-compile-repair
loop actually consumes, not just the raw compiler text.

[#scripting]
== Running a `.ktriz.kts` script

The module `ktriz-script` compiles and runs `*.ktriz.kts` files. `dev.ktriz.core.*`
and `dev.ktriz.function.*` are in scope by default -- no import needed, though
writing one explicitly (as below) is harmless.

=== Build & run

`./gradlew clean check` (see <<building>>) does not produce a `ktriz`
executable -- build the CLI's install image explicitly, then run it directly:

[source,shell]
----
./gradlew clean :ktriz-cli:installDist
./ktriz-cli/build/install/ktriz/bin/ktriz run hello-world.ktriz.kts
----

Note the install directory is named `ktriz`, not `ktriz-cli`
(`ktriz-cli/build/install/*ktriz*/bin/ktriz`) -- `ktriz-cli/build.gradle.kts`
sets `applicationName = "ktriz"` explicitly so the binary and its `ktriz mcp`/
`ktriz run`/`ktriz help` subcommands read naturally, so this does *not*
follow the `<module>/build/install/<module>/bin/<module>` pattern
<<mcp,`ktriz-mcp` below>> uses. The `$ ktriz ...` examples below assume that
binary is on your `PATH` (e.g. via a symlink).

[source,kotlin]
----
// hello-world.ktriz.kts
val problem = contradiction(
    improving = EngineeringParameter.WEIGHT_OF_MOVING_OBJECT,
    worsening = EngineeringParameter.STRENGTH,
)
val principles = problem.resolve()

println("Widerspruch: ${problem.improving.labelDe} ↑  vs.  ${problem.worsening.labelDe} ↓")
println("Empfohlene erfinderische Prinzipien:")
principles.forEach { p -> println("  #${p.id}  ${p.labelDe}  (${p.labelEn})") }
----

[source,shell]
----
$ ktriz run hello-world.ktriz.kts
Widerspruch: Gewicht eines beweglichen Objekts ↑  vs.  Festigkeit ↓
Empfohlene erfinderische Prinzipien:
  #28  Ersetzen mechanischer Wirkprinzipien  (Mechanics substitution)
  #27  Billige Kurzlebigkeit  (Cheap short-living objects)
  #18  Mechanische Schwingungen  (Mechanical vibration)
  #40  Verbundwerkstoffe  (Composite materials)
----

In text mode the script's own `println` output goes straight to stdout, exit
code `0`. Add `--output json` for a single structured JSON document instead --
`ktriz run` captures the script's stdout for you and puts it in the `"stdout"`
field, rather than mixing it into the surrounding JSON:

[source,shell]
----
$ ktriz run hello-world.ktriz.kts --output json
{"status":"success","returnType":null,"stdout":"Widerspruch: Gewicht eines beweglichen Objekts ↑  vs.  Festigkeit ↓\nEmpfohlene erfinderische Prinzipien:\n  #28  Ersetzen mechanischer Wirkprinzipien  (Mechanics substitution)\n  #27  Billige Kurzlebigkeit  (Cheap short-living objects)\n  #18  Mechanische Schwingungen  (Mechanical vibration)\n  #40  Verbundwerkstoffe  (Composite materials)\n"}
----

The `STRUCTURAL_INTEGRITY` case from <<the-compiler-as-oracle,above>> is the
concrete generate-compile-repair signal: a `worsening = ... STRUCTURAL_INTEGRITY`
that does not exist among the 39 parameters fails to compile, and `ktriz run`
reports it structured rather than as a raw stack trace:

[source,shell]
----
$ ktriz run bogus-parameter.ktriz.kts
Script failed to compile:
  [ERROR] (line 10, column 38) Unresolved reference 'STRUCTURAL_INTEGRITY'.

$ ktriz run bogus-parameter.ktriz.kts --output json
{"status":"error","errorKind":"compilation_error","code":"KTRIZ-S-001","diagnostics":[{"severity":"ERROR","message":"Unresolved reference 'STRUCTURAL_INTEGRITY'.","line":10,"column":38}]}
----

Both exit `1`. A generate-compile-repair loop consuming the JSON form reads
`errorKind`/`code` to branch on the failure kind and `diagnostics[].message`
to feed back to the model, without parsing free-text output.

A second, complementary TDG layer sits at runtime rather than compile time: a
parameter *can* contradict itself syntactically (`worsening` given the same
enum member as `improving`), so `Contradiction`'s `init` block enforces that
invariant with `require`, and `ktriz run` reports the resulting
`IllegalArgumentException` the same structured way:

[source,shell]
----
$ ktriz run self-contradiction.ktriz.kts
Script threw at runtime (java.lang.IllegalArgumentException): A contradiction needs two *different* parameters, but both were 'Strength'. A parameter cannot contradict itself.
----

WARNING: A `.ktriz.kts` script is arbitrary Kotlin and runs with **no
sandbox** -- the full rights of the invoking user, the same trust level as
`kotlinc -script` or a `build.gradle.kts` you run locally. `ktriz run` never
resolves a script over the network (a path that looks like a URI, e.g.
`https://...` or `file://...`, is rejected outright, see `SOURCE_REMOTE_URI`
below) and rejects a script file over 1 MiB (`SOURCE_TOO_LARGE`) as a
denial-of-service leitplanke -- neither of those is a sandbox, and a script
within those limits may do anything a trusted local process can do. Only run
scripts you trust.

[cols="1,3"]
|===
| `KtrizScriptOutcome` case | Meaning

| `Success`
| Compiled and ran without throwing. `returnValue`/`returnTypeName` are `null` when the script's last expression was `Unit` (the normal shape for a `println`-based script) -- that is *not* a failure.

| `CompilationError` (`KTRIZ-S-001`)
| Syntax, type, or unresolved-reference error. `diagnostics` holds at least one `"ERROR"`-severity entry with the message/line/column.

| `RuntimeError` (`KTRIZ-S-002`)
| The script threw at runtime. Carries only the exception class and message, never a stack trace.

| `NotEvaluated` (`KTRIZ-S-003`)
| The scripting host returned no result at all.

| `SourceRejected` (`KTRIZ-S-010`..`KTRIZ-S-015`)
| The `.ktriz.kts` file was rejected before anything compiled or ran: a blank path, a URI-shaped path, a missing file, a non-regular file, an unreadable file, or a file over the 1 MiB limit.
|===

[#matrix]
== Contradiction matrix data

The classical Altshuller contradiction matrix is, in substance, generally
treated as public domain by the TRIZ community's goodwill. But a concrete,
digitised *transcription* of that matrix can separately attract an EU sui
generis database right even where the underlying facts are free -- and later,
commercially maintained matrices (Matrix 2003 / 2010 / 2022) remain under
their authors' copyright and are licensed selectively.

kTRIZ ships its own reconciled compilation of the classical 39x39 matrix
(1248 populated cells), built from four independent, freely available
transcriptions rather than copied from any single one: a cell is accepted
when at least two of the four sources agree on it verbatim. kTRIZ ships and
will ship no data from the later Matrix 2003/2010/2022. Full sourcing, the
reconciliation method, and known anomalies are documented in
link:docs/matrix-provenance.adoc[docs/matrix-provenance.adoc]. This closes
the *data* gap ADR-0003 tracked; the *legal* question it also tracked -- the
EU sui generis database right on a concrete transcription -- stays an open,
explicitly unresolved position; see kTRIZ-ADR-0003 for the current status.

The parsing itself, `ContradictionMatrixData.parse(reader, provenance)`, is
the pluggable matrix-source seam ADR-0003 calls for: it is a public, pure
function of any `Reader`, so a user who holds a Matrix 2003/2010/2022 licence
can parse their own file locally into the same shape, without kTRIZ ever
shipping, downloading, or bundling that data itself.

`ContradictionMatrixSource` builds a hardened, discoverable mechanism on top
of that seam:

[source,kotlin]
----
// Programmatically -- hold your own matrix explicitly, ContradictionMatrix's
// process-wide default stays untouched:
val house = ContradictionMatrixSource.fromFile(Path.of("/opt/triz/house-matrix.csv"))
val principles = contradiction(
    improving = EngineeringParameter.WEIGHT_OF_MOVING_OBJECT,
    worsening = EngineeringParameter.STRENGTH,
).resolve(house)
----

[source,shell]
----
# Process-wide, no code change -- applies to ktriz run, ktriz mcp, and any embedding:
java -Dktriz.matrix.file=/opt/triz/house-matrix.csv -jar app.jar

# Via the installed CLI (the application start script passes KTRIZ_OPTS through):
KTRIZ_OPTS="-Dktriz.matrix.file=/opt/triz/house-matrix.csv" ktriz run problem.ktriz.kts
----

The file named by `ktriz.matrix.file` must be an absolute local path (never
a URL -- kTRIZ never downloads matrix data), a regular, readable file no
larger than 4 MiB, strictly UTF-8 encoded, and it is parsed through the exact same
`ContradictionMatrixData.parse` validation the bundled matrix uses -- no
second, laxer path, and the `1..39` parameter-id guardrail (see below)
applies to it exactly as it does to the bundled data. If the override file
is missing, malformed, or otherwise fails to load, kTRIZ aborts rather than
silently falling back to the bundled classical matrix -- a silent fallback
would mean an operator believes they are using their own matrix while
actually getting classical results.

Not supported, on any layer: parsing a Matrix 2003/2010/2022 (48-parameter)
file. `ContradictionMatrixData.parse`'s `1..39` range check is a structural
guardrail (see kTRIZ-ADR-0003), not merely a default -- `EngineeringParameter`
has exactly 39 members, so a cell addressing parameter 42 would be
permanently unreachable through the typed lookup API even if the parser
accepted it.

[#mcp]
== MCP server

kTRIZ ships a Model Context Protocol server, `ktriz-mcp`, exposing the DSL to
LLM agents as tools over stdio. This is the same "compiler as oracle" idea
from <<the-compiler-as-oracle,above>> applied at the protocol level: an agent
that calls `list_engineering_parameters` first, then uses the returned
`symbol` values verbatim, cannot hallucinate a parameter name -- and
`resolve_contradiction`'s matrix lookup is a deterministic table read, never
a generated guess.

=== Build & run

[source,shell]
----
./gradlew clean :ktriz-mcp:installDist
./ktriz-mcp/build/install/ktriz-mcp/bin/ktriz-mcp   # speaks MCP over stdio
----

WARNING: Do not run `./gradlew :ktriz-mcp:run` for a real MCP client. Gradle's
own console output shares stdout with the JSON-RPC stream the server speaks,
so a client reading that stream sees corrupted output. Always launch the
`installDist` binary directly.

Alternatively, once `ktriz-cli` is installed (see <<hello-world>>), the same
server is reachable as a subcommand of the main `ktriz` binary:

[source,shell]
----
./gradlew clean :ktriz-cli:installDist
./ktriz-cli/build/install/ktriz/bin/ktriz mcp
----

Both entry points run the identical `buildServer()`/`runStdioServer()` code
in `ktriz-mcp` -- `ktriz mcp` is a thin wrapper, not a second implementation.
Client configuration below shows the standalone binary; point `command` at
the `ktriz-cli` binary instead (`.../ktriz-cli/build/install/ktriz/bin/ktriz`)
with `"args": ["mcp"]` if you prefer a single installed executable for both
`ktriz run` and `ktriz mcp`.

=== Client configuration

A generic `mcpServers` entry, pointing at the `installDist` binary:

[source,json]
----
{
  "mcpServers": {
    "ktriz": {
      "command": "/absolute/path/to/kTRIZ/ktriz-mcp/build/install/ktriz-mcp/bin/ktriz-mcp"
    }
  }
}
----

=== Tools

[cols="1,2,2"]
|===
| Tool | Purpose | Notable errors

| `list_engineering_parameters`
| Lists all 39 engineering parameters with `id`, `symbol` (the exact Kotlin enum member), `labelEn`, `labelDe`.
| --

| `list_inventive_principles`
| Same shape, for all 40 inventive principles.
| --

| `resolve_contradiction`
| Looks up the classical matrix for `improving`/`worsening` (each accepts a symbol, an English/German label, or a `1..39` id) -- returns the recommended principles in rank order, plus a ready-to-use `contradiction(improving = ..., worsening = ...)` Kotlin snippet.
| `unknown_parameter` (with "did you mean" suggestions), `self_contradiction`, `malformed_input`.

| `build_function_model`
| Builds and validates a `components`/`edges` TRIZ function model without saving or rendering it -- returns the normalized model plus an equivalent `functionModel { }` Kotlin snippet.
| `malformed_input` (e.g. an invalid `quality`).
|===

=== Example call

[source,json]
----
{"name": "resolve_contradiction", "arguments": {"improving": "WEIGHT_OF_MOVING_OBJECT", "worsening": "STRENGTH"}}
----

returns (abbreviated), matching the <<hello-world,Hello World>> output above:

[source,json]
----
{
  "principles": [
    {"rank": 1, "id": 28, "symbol": "MECHANICS_SUBSTITUTION"},
    {"rank": 2, "id": 27, "symbol": "CHEAP_SHORT_LIVING_OBJECTS"},
    {"rank": 3, "id": 18, "symbol": "MECHANICAL_VIBRATION"},
    {"rank": 4, "id": 40, "symbol": "COMPOSITE_MATERIALS"}
  ],
  "empty": false,
  "kotlin": "contradiction(\n    improving = EngineeringParameter.WEIGHT_OF_MOVING_OBJECT,\n    worsening = EngineeringParameter.STRENGTH,\n)"
}
----

Two semantics worth calling out explicitly, because a caller that gets them
wrong ends up in an unnecessary repair loop:

* **An empty `principles` list (`"empty": true`) is a valid result, not a
  failure.** Many cells of the classical 39x39 matrix are legitimately blank
  -- see <<matrix>>.
* **An unrecognized parameter is a structured `unknown_parameter` error with
  suggestions, never a crash.** Call `list_engineering_parameters` first if
  unsure of the exact symbol.

kTRIZ is stateless across tool calls by design: every tool is a pure function
over the fixed 39 parameters, 40 principles, and the immutable contradiction
matrix, with no server-side session state to manage or leak.

== Modules

[cols="1,3"]
|===
| Module | Purpose

| `ktriz-core`
| The DSL itself: `EngineeringParameter`, `InventivePrinciple`, `Contradiction`, `ContradictionMatrix`, `ContradictionMatrixSource`, `functionModel`. Bundles the classical 39x39 contradiction matrix as a classpath resource (`contradiction-matrix-1971.csv`). No dependencies beyond the Kotlin standard library and the `kotlin-logging` facade (no logging backend -- the runnable modules bring their own).

| `ktriz-script`
| The `*.ktriz.kts` scripting host: `KtrizScript`/`KtrizScriptCompilationConfiguration`, `KtrizScriptHost.eval`/`evalSource`, `KtrizScriptOutcome`. `api ktriz-core` (not `implementation`) so `ktriz-core` types resolve inside a script's `wholeClasspath = true` compilation. Deliberately unsandboxed -- see <<scripting>>.

| `ktriz-cli`
| Command-line entry point. `ktriz mcp` (see <<mcp>>); `ktriz run <script.ktriz.kts> [--output json]` (see <<scripting>>); `ktriz help`.

| `ktriz-render-kuml`
| Renders `functionModel { }` to SVG. Depends on `ktriz-core` and kUML's `kuml-layout-api`/`kuml-layout-elk` (layout only, no kUML metamodel/rendering dependency).

| `ktriz-mcp`
| MCP server exposing the DSL to LLM agents as tools over stdio. Depends on `ktriz-core` only -- no `ktriz-render-kuml`; also reachable via `ktriz mcp` in `ktriz-cli` (see <<mcp>>).

| `ktriz-tests`
| Kotest test suite for `ktriz-core`, `ktriz-script`, `ktriz-render-kuml`, `ktriz-mcp`, and `ktriz-cli`.
|===

[#roadmap]
== Roadmap

* Full 39x39 contradiction matrix -- *done* as its own reconciled compilation from four independent transcriptions (two MIT-licensed, two with no licence file), see <<matrix>> and link:docs/matrix-provenance.adoc[docs/matrix-provenance.adoc]; the licence/sui-generis-database-right question on the compilation stays open, see kTRIZ-ADR-0003. The pluggable matrix-source seam is *done*: `ContradictionMatrixData.parse(...)` stays the public parser, `ContradictionMatrixSource.fromFile(path)` is the hardened file-based frontend, and the system property `ktriz.matrix.file` swaps `ContradictionMatrix`'s own data source process-wide with no code change. Explicitly *not* included: Matrix 2003/2010/2022 (48-parameter) support -- such a file is still structurally rejected, because `EngineeringParameter` has 39 members and cells beyond that would be unaddressable through the typed lookup API (see kTRIZ-ADR-0003).
* kUML-based SVG rendering for `functionModel { }` -- *done*, see <<function-model-svg>>. Implemented as Weg B from kTRIZ-ADR-0002 (consume kUML as a library dependency, in-process call; kTRIZ never becomes a kUML dependency, and kTRIZ never modifies kUML core), but narrower than originally sketched: kUML is consumed only as a *layout* library (`kuml-layout-api`/`kuml-layout-elk`), not as a diagram renderer, because kUML's SVG renderer (`kuml-io-svg`) has no generic node/edge diagram entry point and no wavy/doubled-line concept a `FunctionQuality` could map onto. `ktriz-render-kuml` writes its own small SVG emitter on top of kUML's computed node bounds and edge routes.
* MCP server -- *done*, see <<mcp>>. `ktriz-mcp` exposes `list_engineering_parameters`, `list_inventive_principles`, `resolve_contradiction`, and `build_function_model` over stdio, and is wired into `ktriz-cli` as `ktriz mcp` (mirroring kSTEP's `kstep mcp`).
* `*.ktriz.kts` Kotlin scripting host -- *done*, see <<scripting>>. `ktriz-script`'s `KtrizScriptHost` compiles and runs a script with `dev.ktriz.core.*`/`dev.ktriz.function.*` in scope, mapping every outcome into a structured `KtrizScriptOutcome`; exposed as `ktriz run` on the CLI, with a `--output json` mode for machine consumers.
* Real CLI commands -- `ktriz run` and `ktriz mcp` are both *done* (see <<scripting>> and <<mcp>>). Not yet done: a way to call `FunctionModel.renderSvg()` from inside a `.ktriz.kts` script (deliberately left out of this wave's scope -- would need `ktriz-render-kuml`, which pulls in ELK, on the script compile classpath).
* `FunctionModel.renderSvg()` follow-ups, explicitly out of scope for V1: real font-metrics-based node sizing instead of the fixed 140x60 px box; arrowheads on edges; visual separation for multiple edges between the same component pair; a dedicated fixed-radius loop arc for self-loops instead of relying on whatever ELK's `elk.layered` self-loop strategy produces.
